# Git delivery

Read HACKATHON.md and REVIEW-CONTRACT. The parent coordinator executes this only after both independent approvals. Do not treat a green test run as a substitute.

1. Verify correct worktree/branch, no unresolved merge entries, and two APPROVE reports matching brief revision, base, HEAD and current `git write-tree`. Inspect the full staged patch and secret/generated-file risks. `git diff --exit-code` must show no unstaged tracked modifications. Inventory untracked files and confirm no runtime dependency was omitted. Never stage everything blindly. For a pending normal integration merge, also verify MERGE_HEAD equals the recorded source SHA and HEAD is the expected integration base. Ancestry mismatches invalidate delivery even if file trees match.
2. If index, HEAD, brief or code changed since review, stop delivery and re-enter verification/review. No formatter or automatic fix may silently alter the approved candidate.
3. Commit locally with a descriptive title such as `feat(revenue): add period-filtered overview`. Keep hooks enabled. If a hook changes files, fails, or the commit's `HEAD^{tree}` differs from the approved tree, mark it unapproved and rerun checks plus BOTH reviews before any push. Do not bypass hooks or amend shared history. A failed hook may leave staged/unstaged changes; inspect before resuming. If no commit was created, freeze/review the corrected candidate and retry the commit. If a hook-altered commit already exists, record delivery mode `review-existing-commit`, its SHA and actual parents; freeze its complete tree with that SHA as HEAD and review the entire base-to-candidate diff. After both approve that exact tree, finalize the existing commit without creating an empty second commit. Any further fixes use a new approved follow-up commit; do not rewrite the existing commit to hide the event.
4. Confirm final commit SHA, `git rev-parse HEAD^{tree}` equals the approved tree, intended files only, and working-tree status is explained. For normal integration commits verify the parents are exactly the recorded integration base and source SHAs; for an agreed squash verify its single base parent and preserve the source mapping. In `review-existing-commit` mode confirm HEAD is still the recorded already-created commit. Record both reviewer results and check evidence outside the index.
5. Follow existing push/PR permission from HACKATHON.md or the user. When authorized, push the named feature branch to the verified remote without force; create a PR into the agreed integration branch. If remote permission is absent, finish at local COMMITTED and provide the next action. A rejected push is a state/coordination issue: fetch, inspect divergence, preserve both sides, and re-review any combined result rather than force-pushing.
6. PR/handoff: problem and resulting behavior, scope, acceptance/check evidence, both candidate approvals, final SHA, screenshot paths/links where relevant, demo steps, known limitations and conflicting/shared files. Use a body file or structured API for multiline content. Do not publish secrets or local-only paths as if teammates can open them.

Report READY_TO_INTEGRATE only after the branch/handoff is available to the integrator. Do not call local approval or successful push an integrated feature. The integrator must apply `.cursor/skills/git-integration/SKILL.md` to the latest combined tree.
